    Modules 4 et 5 : standalone et traduction

    Standalone : une application sans modules

    Le concept

    Avant, chaque composant devait être inscrit dans un module, comme un salarié rattaché à un service qui lui prête ses outils. Pour savoir ce qu'un composant pouvait utiliser, il fallait lire un autre fichier. Aujourd'hui, chaque composant apporte lui-même ses outils : sa liste imports.

    Des cas réels :

    • une application d'entreprise écrite en Angular 12 compte quarante modules : la migration officielle les retire dossier par dossier, sans réécrire l'application ;
    • une bibliothèque partagée entre plusieurs équipes fournit une fonction provideXxx() au lieu d'un module de configuration ;
    • dans ShopFlow, tout est déjà standalone, mais l'espace vendeurs recopie à la main une partie de la configuration de la boutique (le client HTTP) et oublie l'intercepteur.

    Les outils :

    • imports dans @Component : ce que le template utilise (composants, directives, pipes). Depuis Angular 19, un composant est standalone par défaut.
    • bootstrapApplication et app.config.ts : le démarrage sans AppModule.
    • makeEnvironmentProviders : regroupe des fournisseurs dans une fonction provideXxx(), comme provideRouter() ou provideHttpClient().
    • La migration officielle @angular/core:standalone, en trois modes : convert-to-standalone, prune-ng-modules, standalone-bootstrap.

    Pourquoi Angular a abandonné les modules :

    • chaque composant se déclarait deux fois : dans son fichier et dans un module ;
    • un oubli dans le module donnait l'erreur « is not a known element », loin du composant fautif ;
    • ce qu'un composant pouvait utiliser était caché dans le module, un autre fichier ;
    • charger une page à la demande demandait un module par page.

    Quand s'en servir :

    • tout nouveau code : standalone, sans se poser la question ;
    • une configuration partagée par plusieurs applications : une fonction provideXxx() ;
    • une application à modules : la migration officielle, un dossier à la fois.

    En résumé : le composant déclare ce qu'il utilise ; l'application déclare ce qu'elle fournit, dans app.config.ts.

    Dans la vraie vie : beaucoup d'applications d'entreprise ont encore des modules. On les migre par étapes, en vérifiant que l'application se construit entre chaque étape.

    Traduire l'application

    Le concept

    Un livre traduit ne s'imprime pas avec des notes de traduction en bas de page : on imprime une édition par langue. @angular/localize fait la même chose : il construit une version complète de l'application par langue. La page anglaise est déjà en anglais quand elle arrive dans le navigateur.

    Des cas réels :

    • une boutique de Tourcoing vend aussi en Belgique et au Royaume-Uni : chaque langue est une version construite à part, servie à sa propre adresse (/fr/, /en/) ;
    • une application interne d'un groupe international affiche les dates et les montants au format de chaque pays ;
    • dans ShopFlow, tous les textes sont écrits en dur dans les templates : impossible d'ouvrir la boutique à des clients anglophones.

    Les outils :

    • @angular/localize : la fonction de traduction et l'outil d'extraction.
    • L'attribut i18n sur un élément : marque son texte. Sa valeur aide le traducteur : description@@identifiant. L'identifiant fixe garde la traduction même si le texte français change un peu.
    • i18n-placeholder (ou i18n-title…) : marque un attribut.
    • Les expressions ICU : {n, plural, =0 {…} =1 {…} other {…}} pour les pluriels, select pour les autres cas.
    • $localize : marque un texte écrit dans le code TypeScript.
    • La cible extract-i18n : rassemble les textes marqués dans messages.xlf (format XLIFF, lu par les outils des traducteurs).
    • "localize": true : la construction produit un dossier par langue. Les pipes currency et date suivent la langue de chaque version : 27 845,79 € en français, €27,845.79 en anglais.

    Quand s'en servir :

    • une application publique en plusieurs langues : @angular/localize, une version par langue ;
    • un changement de langue sans recharger la page : une bibliothèque qui charge les traductions pendant l'utilisation (Transloco, ngx-translate), au prix d'un fichier de traductions à télécharger.

    En résumé : on marque, on extrait, on traduit, on construit une version par langue.

    Dans la vraie vie : Transloco et ngx-translate sont fréquents en entreprise. @angular/localize est l'outil d'Angular, sans dépendance et sans téléchargement en plus.

    Module 6 : formulaires

    Un formulaire qui refuse une saisie incomplète

    Le concept

    Un guichet de la poste refuse un colis sans adresse avant de le prendre, pas après l'avoir expédié. Un formulaire réactif fait pareil : chaque champ porte ses règles, Angular les vérifie à chaque frappe, et le bouton d'envoi sait si tout est correct.

    Des cas réels :

    • une banque refuse un virement dont l'IBAN est mal formé, avant même l'envoi au serveur ;
    • un site de réservation vérifie que la date de départ précède la date de retour : une règle sur deux champs ;
    • dans ShopFlow, la page de commande accepte un envoi vide : c'est la ligne 8 du cahier des charges.

    Les outils :

    • FormControl, FormGroup, FormArray : un champ, un groupe de champs, une liste de champs de longueur variable. Ils héritent tous d'AbstractControl (value, valid, touched, hasError()).
    • NonNullableFormBuilder (inject(NonNullableFormBuilder)) : construit le formulaire en peu de lignes ; un champ remis à zéro reprend sa valeur de départ au lieu de null.
    • Validators : required, minLength, email, min, pattern.
    • Un validateur personnalisé : une fonction qui reçoit le contrôle et renvoie null (valide) ou un objet d'erreur ({ codePostal: … }). Placé sur un groupe, il compare plusieurs champs.
    • Dans le template : [formGroup], formControlName, formGroupName, et @let pour nommer un contrôle.

    Les formulaires « pilotés par le template » (ngModel) existent toujours, pour un champ ou deux. Dès qu'il y a des règles, on passe aux formulaires réactifs : les règles sont dans le code TypeScript, typées et testables.

    Quand s'en servir :

    • un formulaire avec des règles ou des messages d'erreur : formulaire réactif ;
    • une règle propre au métier (code postal, IBAN) : un validateur personnalisé ;
    • une règle entre plusieurs champs ou avec une donnée extérieure (le panier) : un validateur sur le groupe.

    En résumé : les règles vivent dans le composant, les messages dans le template, et le formulaire sait à tout moment s'il est valide.

    Dans la vraie vie : tous les formulaires d'entreprise ont des règles. Angular 22 propose aussi des formulaires à base de signaux (@angular/forms/signals), vus à la fin du module sur cette même commande ; le code existant des entreprises est écrit en formulaires réactifs.

    Les formulaires à base de signaux (Signal Forms)

    Avant de commencer : formulaires réactifs ou Signal Forms ?

    La règle, en une phrase : on ne réécrit pas tout. Les nouveaux formulaires s'écrivent en Signal Forms ; les formulaires réactifs qui fonctionnent restent tels quels, jusqu'au jour où l'on doit de toute façon les refaire.

    Que faire, selon votre situation :

    Votre situation Ce que vous faites
    Application en Angular 21 ou plus ancien Formulaires réactifs : les Signal Forms ne sont stables qu'à partir d'Angular 22
    Application existante passée en Angular 22 Les formulaires existants restent réactifs ; les nouveaux s'écrivent en Signal Forms ; un formulaire réactif ne passe en Signal Forms que lorsqu'on le refait en profondeur
    Nouvelle application en Angular 22 Signal Forms pour tous les formulaires
    Un même formulaire Un seul système à la fois ; les outils de mélange (compatForm, SignalFormControl) ne servent que le temps d'une migration
    Une équipe Le lead écrit la règle une fois dans les conventions du projet, et tout le monde la suit

    Dans ce cours :

    • ShopFlow : la connexion et la commande passent en Signal Forms (démonstration, puis exercice 3.2-B) ; le formulaire produit de la partie suivante reste en formulaires réactifs, pour voir les deux systèmes dans la même application, comme pendant une migration ;
    • Cuisto, cet après-midi : reste en formulaires réactifs, comme une application existante qu'on ne réécrit pas.

    Pourquoi Angular a créé les Signal Forms :

    • Angular 22 fonctionne avec les signaux (plus de Zone.js par défaut, computed, resource), alors que les formulaires réactifs reposent sur des observables (valueChanges) et sur leur propre copie des valeurs → deux mécaniques à faire cohabiter : toSignal(formulaire.valueChanges), getRawValue(), markAllAsTouched() ;
    • les Signal Forms partent d'un signal → le formulaire, ses règles et l'affichage suivent la même mécanique que le reste de l'application.

    Leur maturité :

    • formulaires réactifs : depuis Angular 2 (2016), typés depuis Angular 14 (2022) → dix ans de production, de documentation et de réponses en ligne ;
    • Signal Forms : expérimentaux en Angular 21 (novembre 2025), stables depuis Angular 22.0 (juin 2026 ; @publicApi 22.0 dans node_modules/@angular/forms/types/signals.d.ts) → cinq mois de version stable aujourd'hui ;
    • les tutoriels écrits pour la version 21 sont déjà faux sur un point : la directive [field] s'appelle [formField] en 22.

    Ce que les formulaires réactifs font mieux :

    • le recul : dix ans de cas difficiles déjà résolus et documentés, et des équipes qui les connaissent ;
    • les flux RxJS : valueChanges se branche directement sur debounceTime et switchMap, comme la recherche du jour 2 ;
    • modifier le formulaire pendant l'exécution, contrôle par contrôle (addControl(), setValidators()) : une écriture éprouvée sur les formulaires générés ;
    • tout le code existant : aucune réécriture à payer.

    Ce que les Signal Forms font mieux :

    • les données sont un signal typé → this.commande() au lieu de getRawValue() ;
    • la règle et son message s'écrivent ensemble → le template n'écrit plus de clé d'erreur comme hasError('minlength') ;
    • une règle qui lit un autre signal (le panier) se recalcule d'elle-même, comme un computed ;
    • l'envoi est prévu : tous les champs touchés, action appelée seulement si tout est valide, refus du serveur affiché, submitting() pendant la requête ;
    • ils se combinent au reste d'une application à signaux sans conversion (toSignal).

    Mon application est en formulaires réactifs : devrai-je la passer en Signal Forms ?

    • aujourd'hui, non : les formulaires réactifs ne sont pas dépréciés en Angular 22.2.7 (aucun @deprecated sur FormBuilder, FormGroup ni FormArray) → l'application fonctionne et reçoit les mises à jour, sans rien changer ;
    • ng update ne convertira pas vos formulaires : en 22.2.7, aucune migration automatique vers les Signal Forms. ng update garde le comportement de l'application ; en 22.0, il ajoute même des réglages qui conservent l'ancien fonctionnement (ChangeDetectionStrategy.Eager sur tous les composants, strictTemplates: false) ;
    • les migrations vers les signaux sont des commandes facultatives, qu'on lance quand on le décide : ng generate @angular/core:signals (entrées, requêtes, sorties), ng generate @angular/core:control-flow, ng generate @angular/core:standalone (vue ce matin) ; aucune ne concerne les formulaires en 22.2.7 ;
    • si Angular abandonne un jour les formulaires réactifs, ce sera progressif : il déprécie d'abord, puis garde l'API plusieurs versions. Exemple : *ngIf, déprécié en Angular 20 (@deprecated 20.0 dans @angular/common), est toujours présent en 22.2.7 ;
    • donc : passer un formulaire en Signal Forms quand cela rapporte (on le refait, sa synchronisation pose problème, l'équipe est passée aux signaux), pas parce qu'une mise à jour l'impose ;
    • notre prévision, qui n'est pas une annonce d'Angular : le code neuf passera aux Signal Forms, et les formulaires réactifs resteront des années dans les applications existantes, comme les NgModule après l'arrivée du standalone.

    Le concept

    Un formulaire réactif fonctionne comme un brouillon : le FormGroup garde sa propre copie des valeurs, et l'on recopie ce brouillon au propre avec getRawValue(). Avec les Signal Forms, on écrit directement sur la fiche : les données sont un signal, le formulaire est construit autour de lui, et chaque règle se recalcule dès que ce qu'elle lit change, comme un computed.

    Des cas réels :

    • une inscription : la confirmation du mot de passe se vérifie de nouveau dès qu'on modifie le premier mot de passe ;
    • une réservation d'hôtel : le serveur répond « chambre déjà réservée », et le message s'affiche dans le formulaire, comme une erreur de saisie ;
    • dans ShopFlow, la connexion garde le refus du serveur dans un BehaviorSubject à part, et la commande de 3.2-A appelle markAllAsTouched() à la main.

    Les outils, tous importés de @angular/forms/signals :

    • form(modele, schema, options) construit le formulaire autour d'un signal. formulaire.nom est un champ ; formulaire.nom() donne son état : value(), touched(), invalid(), errors().
    • Les règles s'écrivent dans la fonction du schéma : required, minLength, email, pattern. Chacune reçoit le chemin du champ et son message : required(champ.nom, { message: 'Le nom est obligatoire.' }).
    • validate(chemin, fonction) pose une règle personnalisée. La fonction renvoie null quand tout va bien, sinon un objet { kind, message }.
    • [formField] relie un <input> à un champ, à la place de formControlName ou de ngModel. Il écrit aussi required et minlength sur l'élément HTML.
    • [formRoot], sur la balise <form>, prend en charge l'envoi décrit par l'option submission : il touche tous les champs, puis appelle action seulement si le formulaire est valide. Une erreur renvoyée par action, comme le refus du serveur, s'affiche avec les autres.

    Contrairement à signal() et computed(), essayés hier dans le dossier experiences, form() ne fonctionne que dans une application Angular, car il crée un effet (hors application : erreur NG0201). La démonstration se fait donc dans ShopFlow.

    En résumé : le modèle est un signal, les règles et leurs messages sont dans le schéma, et le template relie chaque champ avec [formField] puis affiche ses errors().

    Dans la vraie vie : on lit et on maintient des formulaires réactifs tous les jours ; on écrit en Signal Forms les nouveaux formulaires d'une application en Angular 22.

    Les tests unitaires : un pipe, un service, un guard, un composant

    Avant de commencer : les tests, vue d'ensemble

    Pourquoi des tests automatiques :

    • une modification casse une page que personne n'a rouverte → le client la découvre en production ;
    • un défaut corrigé revient six mois plus tard → personne ne s'en souvient ;
    • solution : des tests qui s'exécutent seuls, à chaque modification, dans la CI.

    Les familles de tests :

    Famille Ce qu'elle vérifie Outil en Angular 22 Dans ShopFlow
    Unitaire une fonction, un pipe, un service, seuls Vitest (par défaut depuis Angular 21), ou Karma et Jasmine le pipe du prix remisé, le panier
    Composant un composant et son template les mêmes, avec TestBed la carte produit
    Intégration plusieurs pièces ensemble TestBed avec le vrai routeur, provideHttpClientTesting() pour simuler l'API le guard et le routeur
    Bout en bout un parcours complet, dans un vrai navigateur Playwright (Protractor est abandonné depuis 2023) la connexion, la commande incomplète

    Mesuré sur ShopFlow : les 11 tests unitaires en 0,03 s ; les 3 parcours Playwright en 11 s, démarrage du serveur compris.

    D'autres tests, à brancher dans la même CI :

    • accessibilité : les règles d'ESLint pour les templates (au jour 1, elles ont trouvé deux défauts sur la carte de Cuisto), ou axe-core dans Playwright ;
    • rendu visuel : une capture comparée à la précédente (toHaveScreenshot() de Playwright) ;
    • performance : Lighthouse, mesuré au jour 1 et au bilan, peut tourner dans la CI (Lighthouse CI) ;
    • contrat d'API : vérifier que l'API renvoie toujours ce que le front attend ;
    • dépendances : npm audit signale les paquets qui ont une faille connue.

    La pyramide :

    • beaucoup de tests unitaires → rapides, et ils désignent la ligne fautive ;
    • quelques tests de bout en bout → lents et plus fragiles, mais ils prouvent que les parcours essentiels (se connecter, commander) marchent encore.

    Les tests à l'heure de l'IA :

    • un assistant de code écrit un test en quelques secondes → écrire le test n'est plus la partie difficile ;
    • ce qui reste au développeur : choisir quoi tester (les règles métier, les parcours essentiels), relire le test (un test qui ne peut pas échouer ne prouve rien), et le faire tourner à chaque modification ;
    • pour un lead : la CI est le garde-fou commun, que le code vienne d'un développeur ou d'un assistant.

    La suite du module : des tests unitaires montrés sur ShopFlow, un défaut corrigé en écrivant le test d'abord, les tests de bout en bout, puis la CI qui lance tout.

    Le concept

    Un garagiste ne rend pas une voiture sans l'avoir essayée. Un test automatique, c'est un essai écrit une fois et refait à chaque modification, en quelques secondes : on sait tout de suite si une correction en a cassé une autre.

    Des cas réels :

    • une équipe refuse toute fusion de branche dont les tests échouent : l'intégration continue les lance à chaque proposition ;
    • une boutique a perdu une journée de ventes parce qu'un calcul de remise arrondissait mal : un test de trois lignes l'aurait vu ;
    • dans ShopFlow, aucun test : la ligne 9 du cahier des charges demande qu'un test vérifie le prix.

    Les outils :

    • Jasmine : la façon d'écrire les tests (describe pour un groupe, it pour un cas, expect(…).toBe(…)). On écrit le comportement attendu en phrases : c'est l'esprit du BDD.
    • Karma : lance les tests dans un vrai Chrome. Depuis Angular 21, les nouveaux projets utilisent Vitest ; Karma reste pris en charge, et ShopFlow l'utilise.
    • TestBed : une petite application Angular pour le test. TestBed.inject donne un service ; TestBed.createComponent crée un composant (fixture), fixture.componentRef.setInput lui donne ses entrées, await fixture.whenStable() attend son affichage.
    • TestBed.runInInjectionContext : appelle une fonction qui utilise inject(), comme un guard.
    • TestBed.tick() : exécute les effect en attente (la sauvegarde du panier).
    • Un faux service ({ provide: AuthService, useValue: { token } }) : le test choisit ce que le service répond.

    Quand s'en servir : une fonction de calcul (pipe), un service qui garde un état, un guard qui décide d'un accès, un composant qui affiche et émet.

    En résumé : on prépare, on agit, on vérifie ; un test par comportement attendu.

    Dans la vraie vie : les tests unitaires tournent à chaque proposition de code ; un projet sans tests est un projet qu'on n'ose plus modifier.

    Corriger un défaut en écrivant le test d'abord (TDD)

    Le concept

    Avant de réparer une fuite, le plombier la montre : il ouvre le robinet et fait voir l'eau qui coule. Après la réparation, il refait le même geste. En TDD (développement piloté par les tests), on écrit d'abord le test qui montre le défaut : il échoue (rouge). On corrige jusqu'à ce qu'il passe (vert). Le test reste ensuite : le défaut ne peut plus revenir sans qu'on le voie.

    Des cas réels :

    • une équipe exige, pour tout défaut signalé, un test qui le reproduit avant la correction ;
    • un calcul de frais de port corrigé deux fois et cassé deux fois : le troisième correctif vient avec son test, et le défaut ne revient plus ;
    • dans ShopFlow, la carte affiche le prix remisé et la fiche le prix sans remise : c'est la ligne 9 du cahier des charges.

    Les outils : les mêmes que ce matin. L'ordre change : le test d'abord, la correction ensuite, un commit après chaque étape pour que l'ordre se voie dans l'historique.

    Quand s'en servir : tout défaut signalé ; toute règle de calcul.

    En résumé : rouge, vert, et le test reste.

    Dans la vraie vie : le TDD complet (tout code précédé de son test) est rare ; « un défaut, un test d'abord » est très répandu.

    Les tests de bout en bout et la couverture

    Démonstration par le formateur, sur son ShopFlow ; les apprenants regardent.

    Le concept

    Une carte routière où l'on surligne les routes déjà parcourues montre d'un coup d'œil celles qu'on n'a jamais prises. La couverture fait pareil avec le code : elle surligne les lignes que les tests ont exécutées. Et un test de bout en bout, c'est un client-robot : il ouvre un vrai navigateur, clique, tape, et vérifie ce qu'il voit.

    Des cas réels :

    • une équipe affiche la couverture dans chaque proposition de code : une baisse se voit avant la fusion ;
    • une boutique fait passer chaque nuit les parcours « se connecter », « commander », « payer » : une panne est vue avant les clients ;
    • dans ShopFlow, trois parcours suffisent à prouver les lignes 7 et 8 du cahier des charges (pages réservées, commande incomplète refusée).

    Les outils :

    • --coverage : npx nx test --watch=false --coverage écrit un résumé et un rapport HTML dans coverage/shopflow/.
    • Playwright (@playwright/test) : pilote Chrome, Firefox et WebKit. page.getByRole, page.getByLabel trouvent les éléments comme un utilisateur les voit ; expect(…).toBeVisible() et toHaveURL attendent tout seuls que la page soit prête.
    • webServer dans playwright.config.ts : lance l'application avant les tests si elle ne tourne pas déjà.
    • npx playwright test --ui : rejoue chaque parcours pas à pas, avec une capture à chaque action.

    Pourquoi Angular a abandonné Protractor :

    • construit sur Selenium WebDriver : lent, et des tests qui échouaient au hasard ;
    • son attente automatique reposait sur Zone.js : elle ne marche pas dans une application sans Zone.js ;
    • l'équipe d'Angular a arrêté son développement ; les nouveaux projets n'ont plus d'outil de bout en bout imposé, et Playwright est le plus utilisé.

    Quand s'en servir : la couverture pour trouver le code jamais testé, pas comme un objectif chiffré ; Playwright pour les quelques parcours qui rapportent de l'argent ou protègent des données.

    En résumé : la couverture montre ce que les tests n'ont pas essayé ; Playwright essaie l'application comme un client.

    Dans la vraie vie : les parcours Playwright tournent dans l'intégration continue, souvent sur plusieurs navigateurs ; on en garde peu, parce qu'ils sont plus lents que les tests unitaires.

    Faire passer les tests à chaque modification : la CI

    Le concept

    Au portique d'un aéroport, chaque passager passe, sans exception et quel que soit son rang. La CI (intégration continue) fait pareil avec le code : chaque modification proposée passe les mêmes vérifications sur une machine neuve, et la fusion est bloquée si l'une échoue.

    Le problème :

    • chacun lance les tests « quand il y pense » → une modification part sans que personne ne les ait lancés ;
    • tout passe sur le poste du développeur → mais le projet ne se construit pas sur un poste neuf (fichier oublié dans le commit, paquet installé à la main) ;
    • solution : la CI rejoue lint, tests et construction à chaque proposition de modification (pull request), puis affiche un résultat vert ou rouge sur la proposition.

    CI et CD :

    • CI, l'intégration continue : lint, tests et construction à chaque modification ;
    • CD, la livraison ou le déploiement continu : la version qui a passé la CI part seule vers un environnement (préproduction, puis production).

    Dans un espace de travail Nx :

    • nx affected ne lance que les projets touchés par la modification (vu au jour 1) → la CI reste rapide quand le dépôt grossit ;
    • les tests Karma ont besoin d'un Chrome sans fenêtre sur la machine de la CI : --browsers=ChromeHeadless.

    En résumé : un fichier de CI dans le dépôt, les mêmes commandes que sur son poste, et aucune fusion sans résultat vert.

    Dans la vraie vie : GitHub Actions, GitLab CI, Azure DevOps ou Jenkins ; le lead regarde le résultat de la CI avant d'accepter une fusion.

    Module 8 : rendu côté serveur

    Envoyer des pages déjà rendues par le serveur

    Démonstration par le formateur, sur son ShopFlow ; les apprenants regardent.

    Le concept

    Un restaurant peut servir les ingrédients avec la recette, ou le plat déjà dressé. Sans rendu côté serveur, ShopFlow envoie une page vide (<app-root></app-root>) et le code qui la construit : le navigateur fait la cuisine. Avec le rendu côté serveur, le HTML contient déjà les 194 produits. Puis Angular s'accroche à la page reçue sans la reconstruire : c'est l'hydratation.

    Des cas réels :

    • un moteur de recherche ou l'aperçu d'un lien sur un réseau social lit le HTML reçu : une page vide n'a ni titre ni produits ;
    • sur un téléphone lent, la page s'affiche avant que le code d'Angular ait fini de se télécharger ;
    • dans ShopFlow, la ligne 10 du cahier des charges : la page doit être rapide sur mobile.

    Les outils :

    • @angular/ssr, installé avec Nx par npx nx g @nx/angular:setup-ssr (avec Angular CLI seul : ng add @angular/ssr) ;
    • RenderMode.Prerender : la page est rendue une fois, à la construction ; RenderMode.Server : à chaque requête ; RenderMode.Client : dans le navigateur, comme avant ;
    • getPrerenderParams : la liste des paramètres à pré-rendre pour une route comme catalogue/:id ;
    • provideClientHydration() : l'hydratation, ajoutée par le générateur ;
    • isPlatformBrowser(inject(PLATFORM_ID)) : savoir si le code tourne dans le navigateur ou sur le serveur (qui n'a ni localStorage ni window).

    Pourquoi Angular Universal (le programme) a été remplacé :

    • des paquets à part (@nguniversal/…) qui sortaient après chaque version d'Angular ;
    • au début, la page rendue par le serveur était détruite puis reconstruite par le navigateur : un clignotement, et le travail fait deux fois ;
    • un serveur Express et un pré-rendu à configurer à la main.

    Depuis la version 17, le rendu côté serveur fait partie d'Angular CLI : @angular/ssr, avec une migration officielle depuis @nguniversal. L'hydratation garde la page reçue du serveur.

    Quand s'en servir : des pages publiques à référencer ou à afficher vite (catalogue, fiche, article) ; pas pour les pages privées (panier, compte, administration), qui restent rendues dans le navigateur.

    En résumé : on choisit, route par route, où et quand la page est rendue ; le code qui touche au navigateur vérifie d'abord qu'il y est.

    Dans la vraie vie : presque toutes les boutiques en ligne rendent leur catalogue côté serveur. Le piège classique est celui de ShopFlow : un service qui lit le localStorage dès sa création.
