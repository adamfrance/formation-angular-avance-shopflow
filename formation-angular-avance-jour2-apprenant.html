Module 1 (fin) : charger à la demande, documenter, ne pas faire travailler l'affichage

Charger à la demande : les pages et les blocs

Le concept

Dans un restaurant, on n'apporte pas tous les plats de la carte dès que le client s'assoit : on apporte ce qu'il commande, quand il le commande. Une application, c'est pareil : le navigateur n'a pas besoin du code de l'administration pour afficher le catalogue.

Des cas réels :

  • une banque en ligne charge l'espace « Bourse » seulement quand le client l'ouvre : la page d'accueil reste légère sur mobile ;
  • un site de petites annonces affiche les commentaires d'une annonce seulement quand on fait défiler jusqu'à eux ;
  • dans ShopFlow, toutes les pages sont dans un seul fichier main de 343 ko : c'est la ligne 1 du cahier des charges.

Les outils :

  • loadComponent dans une route : le composant de la page part dans un fichier à part, téléchargé quand on navigue vers elle.
    { path: 'panier', loadComponent: () => import('./pages/cart/cart').then((m) => m.Cart) }
  • loadChildren : tout un groupe de routes (l'administration et ses pages enfants) part dans un fichier à part.
  • @defer dans un template : un bloc (et les composants qu'il contient) n'est téléchargé et affiché qu'au moment choisi : on viewport (quand il entre à l'écran), on idle (quand le navigateur n'a plus rien à faire), on interaction, on timer(2s). @placeholder s'affiche avant, @loading pendant.

Quand s'en servir :

  • une page que tous les visiteurs n'ouvrent pas (administration, compte, commande) : loadComponent ou loadChildren ;
  • un bloc lourd sous la ligne de flottaison (avis, carte, graphique) : @defer (on viewport) ;
  • un bloc secondaire en haut de page : @defer (on idle) ;
  • la page d'accueil elle-même : elle reste chargée tout de suite (component).

En résumé : loadComponent et loadChildren découpent par page, @defer découpe à l'intérieur d'une page.

Dans la vraie vie : dans toute application de plus de quelques pages ; c'est souvent la première optimisation qu'on fait, et la plus rentable.

Ne pas faire travailler l'affichage pour rien : pipes purs et ChangeDetectorRef

Le concept

Un serveur de restaurant ne revient pas toutes les dix secondes demander « tout va bien ? » à chaque table : il passe quand on lui fait signe. Angular a le même problème : à chaque passage de détection des changements, il relit les expressions des templates. Si une expression appelle une méthode, la méthode est rappelée à chaque passage, même quand rien n'a changé.

Des cas réels :

  • une liste de 500 lignes qui calcule un prix formaté par méthode : la saisie dans un filtre devient lente ;
  • un tableau de bord en temps réel qu'on veut figer le temps de lire un chiffre ;
  • dans ShopFlow, prixFinal() est appelée 194 fois à l'affichage du catalogue et 88 fois de plus pour cinq touches (ligne 3 du cahier des charges).

Les outils :

  • Un pipe pur (@Pipe, pur par défaut) : Angular ne rappelle sa méthode transform que si sa valeur d'entrée change. On remplace {{ prixFinal() }} par {{ p | prixRemise }}.
  • track p.id dans @for : Angular reconnaît chaque produit et déplace sa carte au lieu de la redessiner.
  • OnPush (par défaut en Angular 22) : un composant n'est revérifié que si une entrée change, si un événement de son template se produit, si le pipe async reçoit une valeur ou si un signal qu'il lit change.
  • ChangeDetectorRef : la télécommande d'un composant.
    • markForCheck() : « revérifie-moi au prochain passage » (utile avec OnPush quand une valeur change hors du template) ;
    • detectChanges() : « revérifie-moi tout de suite » ;
    • detach() et reattach() : « ne me revérifie plus » puis « reprends ».

Quand s'en servir :

  • un calcul affiché dans un template : un pipe pur, ou un computed() (cet après-midi) ;
  • une liste : toujours track sur un identifiant ;
  • un affichage qu'on veut figer ou rafraîchir à la main : ChangeDetectorRef ;
  • une valeur modifiée dans un subscribe() avec OnPush : markForCheck(), ou mieux le pipe async ou un signal.

En résumé : un pipe pur pour un calcul de template, track pour une liste, ChangeDetectorRef pour piloter un composant à la main.

Dans la vraie vie : pipes purs et track tous les jours ; ChangeDetectorRef de temps en temps, surtout dans les composants très actualisés (cours de bourse, tableaux de bord).

Module 2 : Zone.js, RxJS, guards et resolver

Zone.js : ce qu'il faisait, ce que change son retrait

Le concept

Zone.js, c'était un concierge posté à l'entrée de l'immeuble, qui prévenait Angular chaque fois que quelqu'un entrait ou sortait, sans savoir si quelque chose avait changé dans un appartement. Angular revérifiait alors l'application.

  • Ce qu'il faisait : Zone.js remplaçait les fonctions asynchrones du navigateur (setTimeout, setInterval, les événements, les promesses, les requêtes) par des versions qui préviennent Angular à la fin de chaque tâche. Angular lançait alors une détection des changements.
  • Pourquoi Angular l'a abandonné (guide officiel « Angular without ZoneJS ») :
    • il ne savait pas si l'état avait changé → une détection plus souvent que nécessaire (6 passages au lieu de 2 dans la mesure ci-dessous) ;
    • un script de plus → à télécharger et à démarrer ;
    • ses versions des fonctions du navigateur → des piles d'appels difficiles à lire ;
    • async et await impossibles à suivre → réécrits à la construction.
  • Aujourd'hui : depuis Angular 21, une nouvelle application est sans Zone.js. Angular revérifie quand un signal change, quand un événement du template se produit, quand le pipe async reçoit une valeur, ou sur markForCheck(). Pour garder l'ancien comportement : provideZoneChangeDetection() et zone.js dans les polyfills.

La mesure sur ShopFlow : deux versions du même ShopFlow, l'une avec Zone.js, l'autre sans (celle du cours), sur le tableau de bord de l'administration, pendant 11 secondes sans rien toucher. La minuterie des dernières commandes actualise toutes les 5 secondes. Le profil de performance de Chrome (onglet Performance), avec la piste « Angular » (fonction enableProfiling() d'Angular) :

Sur 11 secondes Avec Zone.js Sans Zone.js
Passages de détection des changements 6 2
Par actualisation 3 : après la minuterie, à l'arrivée de la réponse, puis encore une fois 1 : à l'arrivée de la réponse, par le pipe async

L'exécution hors zone et les bibliothèques qui servaient à s'en passer :

Outil Ce qu'il faisait Aujourd'hui
NgZone.runOutsideAngular(() => …) Lancer un code fréquent (mousemove, requestAnimationFrame, une minuterie de bibliothèque) hors de la zone, pour qu'il ne déclenche pas de détection ; NgZone.run() pour y revenir Inutile sans Zone.js : un code ne déclenche rien tant qu'il ne touche pas un signal
ChangeDetectionStrategy.OnPush avec le pipe async Limiter la détection aux composants dont les entrées ou les observables changent OnPush est la valeur par défaut depuis Angular 22
RxAngular (rxLet, push) Afficher un observable et rafraîchir seulement le bout de template concerné, même sans Zone.js Les signaux font la même chose, intégrés à Angular
@ngrx/component (*ngrxLet, ngrxPush) Même idée, dans l'écosystème NgRx Idem
Option ngZone: 'noop' au démarrage Démarrer sans Zone.js, en gérant soi-même la détection provideZonelessChangeDetection() (Angular 20), puis le comportement par défaut (Angular 21)

Dans la vraie vie : une application créée avant Angular 21 a souvent encore Zone.js ; la migrer consiste à retirer zone.js des polyfills et provideZoneChangeDetection(), puis à vérifier les écrans qui modifiaient une valeur hors du template sans signal ni pipe async.

RxJS : partager une requête

Le concept

En deux secondes à la machine à café : un observable est un robinet. Chaque personne qui ouvre le robinet (subscribe) fait couler sa propre eau : avec HttpClient, chaque abonné envoie sa propre requête. shareReplay installe un réservoir : la première personne remplit, les suivantes se servent dans le réservoir.

Des cas réels :

  • la liste des pays d'un formulaire, demandée par cinq écrans : une seule requête ;
  • la configuration d'une application, lue au démarrage puis partout ;
  • dans ShopFlow, le catalogue complet est demandé trois fois (catalogue, tableau de bord, stock) : ligne 5 du cahier des charges.

L'outil : shareReplay({ bufferSize: 1, refCount: false }) : le premier abonné déclenche la requête ; la dernière valeur est gardée (bufferSize: 1) et rejouée à chaque nouvel abonné ; refCount: false garde le réservoir même quand plus personne n'écoute.

Quand s'en servir :

  • une donnée qui change rarement et sert à plusieurs écrans : shareReplay dans le service ;
  • une donnée qui doit être fraîche à chaque ouverture (le panier d'un autre utilisateur, un stock en temps réel) : pas de shareReplay ;
  • un état qui change souvent : un signal (cet après-midi).

En résumé : shareReplay transforme une requête par abonné en une requête partagée.

Dans la vraie vie : très courant dans les services de données ; on prévoit toujours un moyen de rafraîchir (une nouvelle requête à la demande).

RxJS : une recherche qui attend la fin de la saisie

Le concept

Quand on cherche un mot dans un dictionnaire, on n'ouvre pas le livre à chaque lettre : on attend d'avoir fini d'écrire. debounceTime fait attendre le flux des frappes : il ne laisse passer une valeur que si rien n'est arrivé pendant un délai.

Des cas réels :

  • la recherche d'un site de voyage interroge le serveur une fois la saisie finie, pas à chaque lettre ;
  • l'autocomplétion d'une adresse ; une recherche lente ne doit pas afficher un ancien résultat par-dessus un nouveau ;
  • dans ShopFlow, la liste des 194 produits est refiltrée à chaque touche : ligne 3 du cahier des charges.

Les outils :

  • Subject : un observable dans lequel on pousse soi-même des valeurs (next()), ici chaque frappe.
  • debounceTime(300) : attend 300 ms de calme avant de laisser passer la dernière valeur.
  • distinctUntilChanged() : ignore une valeur identique à la précédente.
  • startWith('') : donne une première valeur, pour afficher la liste avant toute frappe.
  • combineLatest([a$, b$, c$]) : recalcule dès que l'un des flux change, avec la dernière valeur de chacun.
  • switchMap : quand la recherche part sur le serveur, lance la requête du dernier terme et abandonne la précédente (c'est le cas de Cuisto, ce soir).

Quand s'en servir :

  • un champ de recherche ou de filtre : debounceTime et distinctUntilChanged ;
  • plusieurs critères qui se combinent (recherche, catégorie, tri) : combineLatest ;
  • une recherche sur le serveur : switchMap, qui annule la requête précédente.

En résumé : le flux des frappes, filtré par le temps, puis combiné aux autres critères.

Dans la vraie vie : dans toutes les recherches et les autocomplétions ; c'est l'un des usages de RxJS les plus fréquents.

RxJS au-delà de switchMap : une remise sur toute une catégorie

Le concept

Une tournée de livraison avec trois livreurs :

  • trois colis partent en même temps ; dès qu'un livreur revient, le colis suivant part ;
  • porte close : le livreur repasse un peu plus tard, puis encore un peu plus tard ;
  • adresse qui n'existe plus : le colis est noté « non livré », la tournée continue ;
  • un livreur sans nouvelles au bout d'une heure : on le considère comme perdu ;
  • le tableau de suivi se met à jour à chaque colis : « 4 livrés sur 6 » ;
  • un second ordre de tournée pendant la tournée : ignoré ;
  • le chef peut rappeler tout le monde ; quoi qu'il arrive, le camion rentre au dépôt.

Des cas réels :

  • Google Drive, WeTransfer : vingt fichiers envoyés trois par trois, une barre de progression, une reprise après une coupure, un bouton Annuler ;
  • le back-office d'une boutique : une promotion sur 200 produits, sans dépasser la limite de débit de l'API ;
  • une application de terrain (livreur, technicien) : les saisies faites hors connexion, renvoyées au retour du réseau ;
  • un bouton « Payer » : deux clics, un seul paiement ;
  • dans ShopFlow : l'administration veut « −10 % sur les ordinateurs portables », soit une requête PUT (modifier un produit) par produit, sur l'API DummyJSON.

Les problèmes, avec les seuls opérateurs de base :

  • deux clics sur « Appliquer » → deux lots : deux fois plus de requêtes, et −19 % au lieu de −10 % si le second lot relit les prix déjà baissés ;
  • 200 requêtes parties d'un coup → une API qui limite le débit répond 429 (« trop de requêtes ») : une partie des prix ne change pas ;
  • une coupure réseau d'une seconde → le prix n'est pas modifié, alors qu'un nouvel essai aurait suffi ;
  • un produit supprimé entre-temps (404, « introuvable ») et catchError en fin de flux → tout le lot s'arrête au premier échec, et on ne sait plus ce qui est fait ;
  • une requête qui ne répond jamais → elle garde sa place, le lot ne finit pas ;
  • pas de bouton Annuler → un lot lancé par erreur va jusqu'au bout.

Les quatre opérateurs qui lancent une requête par valeur : seule change la façon de traiter un clic qui arrive pendant une requête.

Opérateur Un clic pendant une requête Exemple réel
switchMap annule la requête en cours, lance la nouvelle une recherche : seul le dernier terme compte
mergeMap lance la nouvelle en plus ; mergeMap(f, 3) : trois à la fois au plus vingt fichiers envoyés trois par trois
concatMap la met en file : elle part à la fin de la précédente les modifications d'un brouillon, enregistrées dans l'ordre
exhaustMap l'ignore tant que la requête en cours n'est pas finie « Payer », « Appliquer », « Se connecter »

Les autres outils du lot :

  • from(tableau) : un flux qui émet chaque élément du tableau, un par un ;
  • timeout(5000) : pas de réponse en 5 s → une erreur TimeoutError ;
  • retry({ count: 2, delay }) : après une erreur, se réabonne, donc renvoie la requête, deux fois au plus ; delay renvoie timer(ms) pour attendre avant l'essai, ou throwError pour abandonner tout de suite ;
  • catchError à l'intérieur de la requête d'un produit : l'échec devient une valeur ({ ok: false }) et le lot continue ; en fin de flux, il arrêterait tout ;
  • scan : comme reduce sur un tableau, mais donne le résultat après chaque valeur : « 4/6 » ;
  • takeUntil(annuler$) : arrête le flux dès que annuler$ émet ; les requêtes en cours sont annulées ;
  • finalize : s'exécute à la fin, que le lot finisse, échoue ou soit annulé : on réactive le bouton.

Quand s'en servir :

  • une recherche, un filtre qui interroge le serveur : switchMap ;
  • un bouton qui envoie (payer, enregistrer, se connecter) : exhaustMap ;
  • des envois dont l'ordre compte (brouillon, file de modifications) : concatMap ;
  • beaucoup d'envois indépendants (fichiers, produits) : mergeMap(f, N) ;
  • toute requête sur un réseau peu fiable : timeout, et retry avec une attente qui grandit ; jamais de nouvel essai sur une erreur 4xx.

En résumé : on choisit l'opérateur d'après ce qui doit arriver à un clic pendant une requête, puis on protège chaque requête (timeout, retry, catchError) sans arrêter le flux.

Dans la vraie vie : switchMap tous les jours ; exhaustMap souvent, sur les boutons d'envoi ; mergeMap avec une limite et retry de temps en temps, dans les envois en lot, les synchronisations et les téléversements.

Réserver des pages : les guards

Le concept

Un videur à l'entrée d'une salle : il regarde le billet avant de laisser entrer, et renvoie vers la billetterie sinon. Un guard fait la même chose devant une route : il répond « oui », ou renvoie ailleurs.

Des cas réels :

  • l'espace client d'une banque renvoie vers la connexion, puis ramène à la page demandée après la connexion ;
  • un back-office n'est ouvert qu'aux administrateurs ;
  • dans ShopFlow, « Mes commandes » et l'administration s'ouvrent sans connexion : ligne 7 du cahier des charges.

Les outils :

  • CanActivateFn : une fonction appelée avant d'activer une route ; elle renvoie true, ou un UrlTree (une adresse vers laquelle rediriger), ou un observable de l'un des deux.
  • CanActivateChildFn : la même chose pour toutes les routes enfants d'une route (l'administration et ses pages).
  • router.createUrlTree(['/connexion'], { queryParams: { retour: state.url } }) : la redirection, avec l'adresse demandée pour y revenir.
  • Un guard ne protège que l'écran : l'API, elle, vérifie le jeton de son côté.

Quand s'en servir :

  • une page réservée aux personnes connectées : canActivate ;
  • toute une section réservée à un rôle : canActivateChild sur la route parente ;
  • une page qu'on ne doit pas quitter avec des modifications non enregistrées : canDeactivate.

En résumé : un guard est une fonction qui répond oui ou qui redirige.

Dans la vraie vie : dans toutes les applications avec un compte ; on les écrit en fonctions depuis Angular 15 (les classes sont dépréciées depuis la 15.2).

Module 3 : les signaux

Les signaux : le panier

Le concept

Un tableau d'affichage dans une gare : quand un horaire change, tous ceux qui le regardent le voient, sans avoir à redemander. Un signal est une valeur qui prévient ceux qui la lisent quand elle change.

Des cas réels :

  • le compteur d'un panier, affiché dans l'en-tête et sur la page panier ;
  • les filtres d'une liste, qui recalculent le nombre de résultats ;
  • dans ShopFlow, le panier est un BehaviorSubject avec deux flux dérivés et le pipe async partout.

Les outils :

  • signal(valeur) : crée un signal ; on le lit en l'appelant (etat()), on le change avec set(v) ou update(f).
  • asReadonly() : une version en lecture seule, à donner aux composants.
  • computed(() => …) : une valeur calculée à partir d'autres signaux, recalculée seulement quand l'un d'eux change, et mise en mémoire.
  • effect(() => …) : un effet de bord (écrire dans le localStorage, envoyer une statistique) relancé quand un signal lu change. On ne s'en sert pas pour calculer une valeur : c'est le rôle de computed.
  • Un signal ne prévient que si sa valeur change : on lui donne toujours un nouveau tableau ou un nouvel objet (update((lignes) => [...lignes, l])), jamais l'ancien modifié.

Quand s'en servir :

  • un état partagé, lu par plusieurs composants (panier, session, préférences) : un signal dans un service ;
  • une valeur déduite d'un état (total, nombre d'articles) : computed ;
  • une synchronisation avec l'extérieur (stockage, analytics) : effect ;
  • un flux d'événements dans le temps (requêtes, saisie) : RxJS reste le bon outil.

En résumé : signal pour l'état, computed pour ce qui s'en déduit, effect pour ce qui en sort.

Dans la vraie vie : tous les jours dans une application Angular récente ; c'est l'écriture recommandée pour l'état d'un composant ou d'un service.

Signaux et RxJS : toSignal et toObservable

Le concept

Un adaptateur de prise de courant : les signaux et les observables ne se branchent pas directement, deux fonctions font le lien.

  • toSignal(obs$) : lit un observable comme un signal (il s'abonne et se désabonne tout seul) ; utile pour une requête ou un flux qu'on veut afficher ou combiner dans un computed.
  • toObservable(signal) : transforme un signal en observable, pour lui appliquer des opérateurs de temps (debounceTime) ou des requêtes (switchMap).

Des cas réels :

  • une liste chargée par HTTP, filtrée par des critères gardés dans des signaux ;
  • une recherche gardée dans un signal, envoyée au serveur après debounceTime ;
  • dans ShopFlow, le catalogue garde ses critères dans des signaux, et la saisie passe par debounceTime.

Quand s'en servir :

  • afficher ou combiner une requête : toSignal ;
  • appliquer une opération dans le temps à un signal : toObservable, l'opérateur, puis toSignal pour revenir ;
  • un état simple : un signal seul suffit.

En résumé : les signaux pour l'état, RxJS pour le temps et les requêtes, toSignal et toObservable pour passer de l'un à l'autre.

Dans la vraie vie : très fréquent dans les applications qui migrent vers les signaux, et dans tous les écrans de recherche.

Correction à coller · dans shopflow

RxJS ou signaux : lequel choisir ?

Le concept

Dans une gare :

  • le tableau des départs donne l'état actuel : on le lit quand on veut, il affiche la dernière information → un signal ;
  • les annonces au haut-parleur sont des événements : chacune compte, et qui n'écoutait pas à ce moment-là l'a manquée → un observable.

La question à se poser : est-ce une valeur qu'on lit (un état), ou des événements qui arrivent dans le temps et qu'il faut traiter (attendre, annuler, réessayer, compter) ?

Les problèmes quand on se trompe d'outil :

  • un état en RxJS (BehaviorSubject et combineLatest) → un état intermédiaire incohérent passe (« 2 articles, 549 € »), des abonnements partout, un pipe async dans chaque template ;
  • des événements dans un signal → deux valeurs identiques n'en font qu'une, seule la dernière compte : des clics et des notifications perdus ;
  • une requête lancée par un effect → ni attente de fin de saisie ni annulation : une réponse lente peut écraser la plus récente ;
  • des réessais, une limite de requêtes, un double clic à gérer avec des signaux → tout à recoder avec setTimeout et des drapeaux.

Le choix, besoin par besoin :

Le besoin L'outil Pourquoi
Un état affiché : panier, filtres, onglet ouvert, utilisateur connecté signal toujours une valeur, lue directement dans le template
Une valeur déduite : total, nombre de résultats computed jamais d'état intermédiaire ; recalculée seulement si besoin
Des événements dont chacun compte : clics, notifications, messages Subject et RxJS un signal fusionne les valeurs identiques et ne garde que la dernière
Attendre la fin d'une saisie toObservable puis debounceTime debounced() existe dans Angular 22, mais reste expérimental
Une requête qui dépend d'un signal ou d'une autre requête RxJS (switchMap), puis toSignal pour afficher la requête précédente est annulée ; pour une simple lecture, httpResource (stable depuis Angular 22) fait de même
Envoyer, réessayer, limiter le nombre de requêtes, ignorer un double clic RxJS : exhaustMap, mergeMap, retry aucun équivalent en signaux
Un flux continu : minuterie, WebSocket, position GPS RxJS, puis toSignal le temps est le domaine de RxJS

Dans ShopFlow, ce que vous avez déjà écrit :

  • le panier : signal et computed, un état partagé (2.3-A) ;
  • le catalogue : les critères en signaux, la liste en computed, la saisie en RxJS (debounceTime), entre toObservable et toSignal ;
  • « Mes commandes » : RxJS (switchMap, catchError), une requête qui dépend d'une autre ;
  • les commandes en direct : RxJS (timer, switchMap), un flux dans le temps ;
  • le lot de remises : RxJS (exhaustMap, mergeMap, retry), des envois orchestrés.

Quand s'en servir :

  • ce que le template affiche : un signal ;
  • ce qui arrive dans le temps : RxJS jusqu'au bout du traitement, puis toSignal pour l'afficher ;
  • en cas de doute : un signal d'abord, RxJS dès qu'il faut attendre, annuler, réessayer ou ne perdre aucun événement.

En résumé : les signaux pour l'état, RxJS pour le temps, toSignal et toObservable à la frontière.

Dans la vraie vie : les deux cohabitent dans presque chaque écran d'une application Angular récente ; les signaux remplacent les BehaviorSubject pour l'état, RxJS reste l'outil des requêtes orchestrées et des flux.
